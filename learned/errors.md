# Learned: error messages and what they mean

Format: `Error: "<exact text>" -> <meaning and fix>. Confirmed (YYYY-MM-DD). Proof: <source>.`

- Confirmed (2026-10-27): `Error: "Matcha:81: Cannot use '...' outside of a vararg function"` ->
  **`...` was used inside a nested closure.** A wrapper written as
  `local function fire(remote, ...) return pcall(function() remote:FireServer(...) end) end`
  is a parse error: `...` is only legal in the function that declares it, never in a closure
  created inside it. The whole chunk fails to compile, so nothing runs - not even the version
  print. Fix: pack the varargs in the outer function and unpack inside the closure:
  `local function packArgs(...) return { n = select('#', ...), ... } end`,
  `local a = packArgs(...)`, then `unpackFn(a, 1, a.n)` with `local unpackFn = table.unpack or unpack`.
  Proof: Restaurant Tycoon 3 v4.0.0 died at load with this exact error; the v4.0.1 pattern was
  verified live in `matcha_exec` (`V2 unpack true`, `V5 unpack 1`).
- Confirmed (2026-10-27): **this is the second parse error of the "nothing runs at all" family.**
  With `Expected identifier ... got 'until'` (reserved word as a table key) and
  `Expected ')' ... got 'if'` (multi-line statement), the lesson repeats: when a freshly pushed
  script "does nothing", read the console for a parse error **before** re-reasoning about game
  behaviour, because a compile failure means the code was never exercised.
- Confirmed (2026-10-27): **a repo read can return a short truncated body and a failed listing that both succeed on retry, so a "corrupt file" conclusion from one read is unsafe.** `get_file_contents` on `bobashid/roblox-matcha` path `Hub` returned a 4-line body (unclosed ```lua fence, `-- VERSION 2.2` twice) at the branch ref and again at the returned commit sha; a third read at the real blob sha `9f0e9fd2` returned the full 6,038-byte file with `PLACES` and `SCRIPTS` intact. In the same turn a root listing of that repo returned `false` / `text` twice before succeeding and listing all 16 files. Fix: when a body looks truncated or a listing returns `false`, read again by blob sha (from the listing's `sha` field) and treat only the full body as real. Never report a file as corrupted on one read. Proof: the three `Hub` reads and the root listings in this session.
- Confirmed (2026-10-27): `Error: "failed to get git tree: Invalid object requested. SHA must identify a commit or a tree."` -> **a commit sha was passed in the tool's `sha` field instead of a blob sha or a git ref.** The `sha` argument of `get_file_contents` wants a commit/tree ref, not the blob sha the listing returns for a file. Fix: use `ref` for a branch and pass a blob sha only as `sha` when reading that single file, or read by `ref` and let the tool resolve it. Proof: reading `Hub` with `sha=0b9f6de5...` (the commit, not the blob) returned this error while `sha=9f0e9fd2...` (the blob) returned the file.
- Confirmed (2026-10-27): `Error: "Matcha:317: Expected ')' (to close '(' at line 311), got 'if'"` -> **a statement spans several lines and the parser loses the bracket.** The usual cause is a `print(...)` or table constructor written across lines with `..` at the start of continuation lines; one missing or extra close paren then surfaces far below the real mistake, so the reported line is not where the bug is. The chunk never compiles, so nothing runs at all - not even the version print. Fix: put every statement on one line, or build the string in a local first and pass that single variable to `print`. Proof: Realistic Home Defense v7.0 died at load with this error; v7.1 rewrote every print as one line.
- Confirmed (2026-10-26): `Error: "Matcha:548: attempt to index nil with 'Connect'"` -> **the event being connected is nil**, most often `Player.CharacterAdded`. The chunk dies at that line: prints after it never run, so the script looks loaded (widgets already built) but `_G` is never registered and nothing later exists. Fix: guard with `if obj.Event ~= nil then pcall(function() obj.Event:Connect(fn) end) end`, or poll instead. Proof: Realistic Home Defense v4.0 console, where `tab widgets built` appeared but no loaded line did.
- Confirmed (2026-10-26): `Error: "validating \"arguments\": validating root: required: missing properties: [\"owner\" \"repo\"]"` -> **the tool call was malformed, so nothing ran.** Cause: the call's fields were nested inside an extra `arguments` object instead of being the top-level properties. Nothing was written and no read-back happened; do not report the intended write as done. Fix: re-issue with flat properties. Proof: three brain writes in one block returned only this validation error while a correctly shaped call to the same tool in the same turn succeeded.
- Confirmed (2026-10-26): `Error: "Matcha:129: Expected identifier when parsing expression, got 'until'"` -> **a Lua reserved keyword was used as a bare table key.** `until` (and `end`, `for`, `do`, `then`, `else`, `in`, `not`, `and`, `or`, `local`, `function`, `repeat`, `while`, `if`, `return`, `break`, `nil`, `true`, `false`) cannot be written as `{ until = x }`. The whole chunk fails to compile, so **nothing runs at all** - not even the version print, which is why the failure looks like "the script did nothing". Fix: rename the field (`until` -> `due`) or use bracket syntax `{ ["until"] = x }`. Proof: Piano Rhythm Tiles v2.9 died at load with this exact error; v2.10 renamed the field to `due` and read back clean.
- Confirmed (2026-10-26): **a compile error means the file never ran, so a "does nothing" report after a push is not evidence about the game.** Check for a console parse error before re-reasoning about timing or lanes. Proof: v2.9's only symptom was this error; the behaviour it was meant to deliver was never exercised.
- Confirmed (2026-10-26): **two write results returning the same sha and size for two different paths** means the writes did not land as intended. Treat both as corrupt. Fix: re-read each path, compare the returned text against what was sent (spelling, duplicated sections, missing words), rewrite in full, read back again. Proof: a Ride A Dino brain push returned sha `f2a8c41d...` / 2,814 B for both `learned/patterns.md` and `learned/api-facts.md`; the read-back showed `CurriedDino` where `CarriedDino` was sent, one section duplicated, and words missing.
- Confirmed (2026-10-26): a read-back that returns only a heading, or returns another file's heading, is corruption or ordering trouble - not a successful read. Proof: same push as above, where the `api-facts.md` read returned `# Learned: patterns that worked`.
- Confirmed (2026-10-26): **a read-back can carry stray markup or duplicated lines.** Seen on `games/Piano Rhythm Tiles.md`: the text ended with a literal `</content></parameter>` block and repeated its final `Drawing` bullet twice. A write response reporting a fresh sha does not prove the stored body is clean - always read the tail. Proof: that read-back, this session.
- Confirmed (2026-10-26): a stale `sha` in `create_or_update_file` fails visibly (409 / mismatch), so it is safe to write with the last known sha and retry with a fresh read if it errors. Never silently overwrites. Proof: repo writes in this session that succeeded only after a re-read sha.
