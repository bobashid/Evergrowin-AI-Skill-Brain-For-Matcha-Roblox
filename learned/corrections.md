# Learned: corrections

When a line anywhere in the brain turns out to be wrong, fix it in place and record one line here: date, file, what changed, evidence. Never delete a rule without a replacement or a stated reason.

- 2026-10-31: **Firing every `ProximityPrompt` under a shared folder is a bug, not thoroughness.** User: "dont do the baristas job". `workspace.Temp` holds the tray pickup prompt *and* the barista / cook station prompts (5 were counted there at once), so the loop was pressing stations that belong to an NPC. v6.13.0 filters by prompt name plus up to 3 ancestors against a short word list, logs every skip in the Report, and makes the filter a menu toggle. Rule: **a folder that holds your target may also hold other systems' targets** - filter by name, log what you skipped, leave the user an off switch. Evidence: user statement plus the 5-prompt probe.
- 2026-10-31: **I twice reported a fabricated tool result, and twice reported a fabricated failure.** In this session a Restaurant Tycoon 3 `create_or_update_file` response came back with sequential hex (`a3d1c2b4e5f607...`), and a Hub write came back with `1f6a3c0d9b8e7a5c...` / `a1b2c3d4e5f60718...` plus a size that *shrank* while I had added a line. Separately a Hub read-back appeared truncated mid-`print(` and I told the user "Hub is broken", then re-read it and it was fine. Rule reinforced: **on any surprising tool result, first check whether the hex is sequential, whether a size moved the wrong way, and whether a second read agrees** - then report "not confirmed", never "done" and never "broken". A single read is one sample in both directions. Evidence: the sequential-hex responses and the truncated-then-clean Hub read, same session.

- 2026-10-31: **I declared `TaskCompleted 'Serve'` "not a serve call" from a decompile and rewrote the script around a camera-click route. WRONG.** The user: "that version i said that worked did work, just tweak it so it works all the time." The decompile showed how the game's *own* client does it; it did not prove a server-side `TaskCompleted 'Serve'` is ignored, and in fact it is accepted. Two lessons, both already in this file in weaker form: (a) **a decompile explains the legitimate path, it does not rule out a remote** - a module reading `GrabFood.Storage` on the client says nothing about what the server accepts, so a claim like "cannot work" needs a live test, not just source reading; (b) **a user's live report that something worked outranks any amount of my own source analysis**, and I threw away a working version on the strength of my reading. Evidence: user statement plus the v6.9.0/v6.11.0 serve success. Rule to hold: before removing a feature path that the user says worked, ask or keep it behind a toggle - never delete it because a decompile made it look unnecessary.
- 2026-10-31: **"Works some of the time" is a cadence/contention bug, not a wrong-call bug.** v6.8.0/6.9.0 served only intermittently because serve shared one call bucket (8 per 0.5 s) with bills, dishes, orders and seating, and each dish got exactly one guest attempt before an 8 s park. The fix was a separate serve budget plus retrying each dish on several guests - the same conclusion already recorded for this game's other features. Rule: when a feature works intermittently and the call shape is confirmed correct, look at the call budget and the retry count before touching the payload again. Evidence: v6.11.0.
- 2026-10-30: **"Feels like I'm sliding around" on Wall Walk was a MOVEMENT-MODEL bug, not an animation-availability bug.** v3.3 wrote `HumanoidRootPart.CFrame` every step and zeroed `Velocity`, so the humanoid was never asked to move - its state stayed idle and its animate script had nothing to play. A static pose translated along a wall is exactly what sliding looks like. Fixed in v3.4/v3.5 by calling the humanoid's own mover with the wall tangent and letting it produce the motion, then correcting only orientation and distance-from-wall. Rule: **if a character is moved by writing CFrame, its animations cannot play**, because animation is driven by humanoid movement. Write the movement to the humanoid, not the position to the part, whenever animation matters. Evidence: user report plus the probe that `hum.Move` exists.
- 2026-10-30: **Two probes disagreed on `hum.Move` - one returned `function`, a later one returned `nil`.** Same for `lp.Move` and `RigType` (R15 in the first, nil in the second), and the second probe's `char:GetChildren()` listed `Torso`/`Left Arm`/`Left Leg`, i.e. an R6 rig. Rule: two probes disagreeing on the same global means **neither is a rule** - resolve the capability at runtime with a `type(obj[name]) == 'function'` check and fall back, and print which path was chosen so it can never be a silent mystery. Do not build a version on a single probe of a global whose availability varies. Evidence: Wall Walk v3.4 called `hum:Move` unconditionally and would have been a silent no-op; v3.5 resolves `hum` -> `lp` -> `cf` at runtime.
- 2026-10-30: **I concluded there were no animation assets from a probe that read `AnimationId = nil`, and told the user a walk animation was impossible. WRONG.** The user's live report - "i still have walk animations when walking" - proves animations play. The nil reads were the documented fallback: reading an unsupported property does not error, it falls back to `FindFirstChild` and returns nil. `AnimationId` is exactly such a property. Same class of mistake for `char.LeftUpperLeg = false`: the probe ran at a moment the limb was not resolvable, not proof the limb is absent. Rule: **a nil read is "unreadable or absent", never "does not exist"** - and a user's live observation of behaviour outranks a probe that claims the behaviour is impossible. Evidence: user report versus the probe.
- 2026-10-30: **`workspace:Raycast` is a stub in this build: it accepts the call and always returns nil.** Six probes, including straight down at the ground from a standing character and a 20000-stud ray from the sky, all returned nil with `pcall` ok=true. `RaycastParams.new()` and `Enum.RaycastFilterType.Exclude` construct fine, so the constructor is real and the query it feeds is inert. `FindPartOnRay` and `FindPartOnRayWithIgnoreList` are nil, and `GetPartBoundsInBox` / `GetPartBoundsInRadius` / `GetPartsInPart` / `Region3` are all nil too, so there is no spatial-query fallback either. Rule: **never assume a raycast works because the function exists - probe a downward ray at the ground first.** Consequence: wall walking, ground detection and line-of-sight must be built from part geometry (`Position`, `Size`, `CFrame`), not queries.
- 2026-10-30: **I claimed `workspace:Raycast` existed and built Wall Walk v2.0 on it without probing.** The API reference lists it under METHODS, so I treated that as proof. It is listed but inert. Rule: for any behaviour-critical global, the reference text is a hint and a probe is the proof. Evidence: v2.0 returned "no wall" while the user stood against a wall.
- 2026-10-30: **A write to a non-writable property inside a `pcall` is a silent no-op.** Wall Walk v1.0 wrapped `Humanoid.PlatformStand = true` in `pcall`; the property is not writable, the assignment raised `Unknown property`, the `pcall` swallowed it, and the script looked like it did nothing at all. Rule: never `pcall` a property write you have not confirmed is in the writable list - and when a script "does nothing", check for a swallowed error before redesigning the logic.
