# Learned: API facts and signatures

Proven by a probe, log or the docs. Format: `Confirmed (YYYY-MM-DD): <fact>. Proof: <source>.` When a fact corrects an `api-*` reference file, fix that line there too and note it in `learned/corrections.md`.

- User-stated (2026-11-03, from a working community script for Violence District): **the real Matcha menu widget API, as actually called.** This is the first dump that shows the live names instead of a retry ladder, so prefer these over the `safeToggle` ladders when they work:
  ```lua
  local M = _G.UI                       -- the menu object; AddTab is the entry point
  M.AddTab("Tab Name", function(tab) ... end)      -- callback re-runs, guard with a built flag
  local sec = tab:Section("Name", "Left")          -- side is required ("Left" / "Right")
  sec:Toggle(id, label, default, callback)
  sec:SliderInt(id, label, min, max, default, callback)
  sec:Keybind(id, defaultKey, mode)                 -- mode: "toggle" | "hold" | "always" | "click"
  sec:ColorPicker(id, r, g, b, alpha, callback)     -- callback receives (colour, alpha)
  sec:ColorPicker2(id1, {r,g,b,a}, id2, {r,g,b,a}, callback)
  sec:Button(label, callback)
  sec:Text("line") / sec:Tip("line") / sec:Spacing()
  M.GetValue(id) / M.SetValue(id, v) / M.RemoveTab(name)
  ```
  Keybind widgets additionally expose `:IsEnabled()`, `:GetKey()`, `:GetType()`, `:AddToHotkey(label, toggleId)` (puts the bind in Matcha's on-screen hotkey overlay while the toggle is on) and a writable `.value`. Two gotchas the script had to handle: **`M.SetValue` only writes the stored value and leaves the widget itself alone**, so a programmatic flip must also write `w.value` / `w:SetValue(v)`; and **a ColorPicker can read back as a bare number** rather than a Color3 (measured: it is the red channel, 139/255), so any colour read needs a total `asColour` guard accepting number / table / userdata before indexing `.R`.
- User-stated (2026-11-03, from the same script, whose author measured it): **`game:GetService(name)` can return `nil` in this VM, intermittently, even for `Players` and `RunService`** - and it can return nil in the same second that the global `workspace` is fine. The services are still children of the DataModel, so the working fallback chain is: retry `GetService` a few times -> `game:FindFirstChild(name)` -> walk `game:GetChildren()` matching `ClassName == name` (some service `Name`s read as empty strings, so match ClassName). `Workspace` should fall back to the global `workspace` first. Consequence: a script that does `local P = game:GetService("Players")` then `P.LocalPlayer` at the top level can die with "attempt to index nil with 'LocalPlayer'" purely because the game had not finished attaching. Proof: the script's own header comment, plus its three-route `LocalPlayer` resolution (cached service -> fresh `GetService` -> `game.Players`).
- User-stated (2026-11-03, from the same script): **a loaded chunk cannot yield at its top level in this VM, and `task.delay` never fires.** The script states both directly: blocking at the top of a chunk "dies silently", so a not-ready game is handled by queueing a retry (`task.spawn` loop that re-reads and re-runs the file via `readfile` + `loadstring` once the services resolve) instead of `task.wait`; and a scheduled press is parked as a deadline serviced by a tick loop because "Matcha's `task.delay` never fires (it is a deadline, not a scheduler)". NOTE: `api-globals-limits-pitfalls.md` records `task.delay` as FIRING, so this is a direct conflict - resolve it with a probe (`task.delay(0.2, function() print('x') end)`) before relying on either.
- User-stated (2026-11-03, from the same script): **`:GetAttribute` costs roughly 606 microseconds per call in this game**, which is why its parry gate set is cached at 5 Hz instead of read on the press path. Consequence: an ESP or trigger loop that reads a handful of attributes per candidate per frame is spending milliseconds it does not have; read them on a slower tick and cache. Also measured in that script's game: `Players:GetPlayers()` and `Players:GetChildren()` can return an empty list mid-round, so entity discovery has to fall back to walking `Workspace` by attribute.
- User-stated (2026-11-03, from the same script): **`Drawing.new("Image")` accepts a raw BMP byte string via `.Data`.** The bundled UI library builds 24-bit BMPs in pure Lua (a `BM` header + a 40-byte DIB + bottom-up pixel rows padded to 4 bytes, BGR order) and assigns the result to `Image.Data` to get a colour-picker gradient and a vector logo. Useful when a widget needs a bitmap and there is no asset id to load.
- Confirmed (2026-11-02, PROBED): **a composite rotation write to `HumanoidRootPart` works and does not move the character.** `root.CFrame = CFrame.new(p.X,p.Y,p.Z) * base * CFrame.Angles(pitch, 0, roll)` returned ok with **position drift 0.0000**; a 0.6 rad pitch + 0.25 rad roll took the up vector 1.000 -> 0.800 and `RightVector.Y` to -0.600 (i.e. a real diagonal tilt, not just pitch), and restoring `base` returned up to 1.000 exactly. Consequence: a topple can combine pitch and roll on a captured basis, which is what makes a non-forced, diagonal fall possible without any velocity write. Proof: `matcha_exec` this session, `mulWrite true nil` / `posDrift 0.0000` / `restored up 1.000` and `base ok / rollWrite ok / upY 0.800 rightY -0.600 / restored upY 1.000`.
- Confirmed (2026-11-02, PROBED, and it CONTRADICTS the 2026-10-30 entry below): **`Motor6D.C0` is NOT readable in the current build, and `Part0` / `Part1` / `Enabled` are unknown properties.** Probe on a live R6 character read `C0` as `nil` for all five torso joints (Right/Left Shoulder, Right/Left Hip, Neck) and the write failed with `invalid argument #1 (CFrameMeta expected, got nil)`. `m.Part0` and `m.Part1` read nil; writing `m.Part0` raised `Unknown property: Part0`; `m.Enabled` read nil (typeof nil), so the joint-disable ragdoll route is closed too. Consequence: the limb-flop in Player Trip cannot work on this build and must be treated as optional, self-disabling code. Proof: `matcha_exec` this session printing `joint Right Shoulder C0 nil` / `C0 write false ... CFrameMeta expected` / `p0Write false ... Unknown property: Part0`. This is one sample; the 2026-10-30 probe said the opposite, so per the two-probes-disagree rule, resolve it at runtime with a `type(c0) == 'userdata'` check rather than assuming either way.
- Confirmed (2026-11-02, PROBED): **angular velocity is not exposed at all.** `AssemblyAngularVelocity`, `AngularVelocity` and `RotVelocity` all read `nil` on `HumanoidRootPart` and writing any of them raised `Unknown property`. `AssemblyLinearVelocity` and `Velocity` both read as a Vector3 and are the only motion levers. Consequence: a spin or tumble cannot be applied by the script; any rotation has to come from writing `CFrame`. Proof: `matcha_exec` this session, `AAV write false Matcha:14: Unknown property: AssemblyAngularVelocity`.
- Confirmed (2026-11-02, PROBED, reconfirms 2026-10-30): **`Humanoid.PlatformStand` is not writable.** Read returns nil, write raises `Unknown property: PlatformStand`. With `Motor6D.Enabled` also unwritable and `Instance.new` nil (no BallSocketConstraint), there is **no way to make a real physics ragdoll** in this VM; the closest honest substitute is a rotation the body falls out of, with no velocity writes. Proof: `matcha_exec` this session, `PlatformStand write false Matcha:14: Unknown property: PlatformStand`.
- Confirmed (2026-10-30, PROBED earlier this session): **Motor6D joints on the character are readable AND writable, so limbs can be posed.** An R6 character's Torso holds six Motor6D joints (Neck, Left Shoulder, Right Shoulder, Left Hip, Right Hip, RootJoint). `motor.C0` reads as userdata (ok=true); a write to `motor.C0` returns ok=true err=nil; and the written value STICKS on read-back 0.05 s later. Consequence: limb-level posing IS possible even though there is no Humanoid state machine - a ragdoll flop, a static pose or a custom idle can be built by writing each joint's C0, then restoring the captured rest C0 to recover. This is the route Player Trip v2.0 uses. Caveat on the proof: a re-probe attempt later in the session failed with `Tool matcha_exec not found`, so this rests on the earlier probe in the same session, not on a fresh one. **SUPERSEDED as a rule by the 2026-11-02 probe above (C0 nil, five joints not six).** Proof: `matcha_exec` printing `motors=6`, `c0ok=true type=userdata`, `writeok=true err=nil`, `rbok=true type=userdata`.
- Confirmed (2026-10-30, PROBED): **there is no Humanoid state machine in this build.** `ChangeState`, `SetStateEnabled`, `GetStateEnabled`, `GetState`, `PlayEmote` and `LoadAnimation` are all nil on the Humanoid; calling `GetState` raised `attempt to call missing method 'GetState' of Instance`. `Enum.HumanoidStateType` is nil too, so `Enum.HumanoidStateType.FallingDown` cannot even be named. Consequence: a script cannot put the character into FallingDown, Ragdoll, Physics or any other state, so the classic `hum:ChangeState(0)` trip/ragdoll idiom cannot be ported at all. What remains writable, from the same probe: `root.CFrame` and `root.Velocity`, both userdata. The workaround is to fake the pose - a rotated root CFrame plus a Velocity push, and joint C0 writes for the limbs. Proof: `matcha_exec` probe printing `ChangeState=nil SetStateEnabled=nil GetStateEnabled=nil GetState=nil PlayEmote=nil LoadAnimation=nil`, `FallingDownEnum=nil`, and `rootCF=userdata rootVel=userdata`.
- Confirmed (2026-10-30, PROBED): **`CFrame.fromMatrix` and `CFrame.fromAxisAngle` are nil in this build.** `type(CFrame.fromMatrix)` returned `nil` and calling it raised `attempt to call a nil value`. `CFrame.Angles` and `CFrame.lookAt` exist but cannot build an arbitrary orientation: `CFrame.lookAt(pos, target, up)` **ignores the `up` argument** - passing up=(1,0,0) returned `UpVector (0,1,0)`. So `CFrame.new(x,y,z, rX,uX,bX, rY,uY,bY, rZ,uZ,bZ)`, the 12-number form, is the **only** constructor here that sets a custom basis. The vectors are the COLUMNS of the rotation matrix, in the order right, up, back. Proof: `fromMatrix=nil fromAxisAngle=nil Angles=function`, then `cfL up=Vector3(0.0000, 1.0000, 0.0000)` after passing up=(1,0,0), then `cf12 ok=true` with `built up=1.00,0.00,0.00 built right=0.00,-1.00,0.00`.
- Confirmed (2026-10-30, PROBED): **a rotated CFrame write to `HumanoidRootPart` persists across a physics step** - the humanoid does not snap the character upright. A basis with up=(1,0,0) read back `UpVector (1.00,0.00,0.00)` immediately and still `(1.00,0.00,0.00)` after 0.1 s. **But gravity still acts**: in that same 0.1 s Y fell from `24.00` to `23.02`. Consequence: rotation alone does not hold you in place - Position must be rewritten every physics step, and that rewrite is what cancels the fall. Proof: same probe, `imm up` / `later up` / `later posY=23.02 wasY=24.00`.
- Confirmed (2026-10-30, PROBED): **there are no animation assets loaded and no way to load one**, but animations DO play because the game's own `Animate` script drives them. `Animate` has 10 children (`idle, walk, run, jump, climb, toolnone, fall, sit` plus a `PlayEmote` BindableFunction and a `ScaleDampeningPercent` NumberValue) whose `Animation` children read `AnimationId = nil` - that is the unsupported-property fallback, not proof of absence. `Humanoid.LoadAnimation` and `Animator.LoadAnimation` are both nil. Consequence: never conclude "animations are impossible" from a nil `AnimationId`; the reliable test is whether the humanoid is *moving*, because that is what the animate script keys off. Proof: user live report ("i still have walk animations when walking") versus the nil reads; corrected in `learned/corrections.md`.
- Confirmed (2026-10-30, PROBED): **`workspace:Raycast` exists as a function but NEVER RETURNS A HIT in this build - it returns nil for every ray, everywhere.** Six independent casts all returned nil: 3 studs forward along the flattened look vector; 50 studs forward; 50 studs down from a character standing on ground; 300 studs down; 900 studs down from 300 studs above; and a 20000-stud ray from (-5000, 5000, -5000). `pcall` returned ok=true every time - a stub, not an error. `RaycastParams.new()` and `Enum.RaycastFilterType.Exclude` construct fine, so the constructor is real while the query it feeds is inert. Consequence: **no query can detect a surface in this VM**; detection must come from part geometry (`Position`, `Size`, `CFrame`). Proof: `matcha_exec` probes this session.
- Confirmed (2026-10-30, PROBED): **`workspace.FindPartOnRay` and `workspace.FindPartOnRayWithIgnoreList` are nil**, and `GetPartBoundsInBox`, `GetPartBoundsInRadius`, `GetPartsInPart`, `Region3` are all nil too. No legacy or volume-query fallback. Proof: `FindPartOnRay=nil WithIgnoreList=nil Ray=table` and `boxQ=nil radQ=nil inPart=nil r3=nil Region3=nil`.
- Confirmed (2026-10-30, PROBED): **a large part's face can be within reach while its CENTRE is far away.** A 5x2x5 part whose face was 2 studs from the player had its centre 22.59 studs away. A broad-phase that skips parts by centre distance alone silently drops large walls; the correct conservative test is `centreDistance - halfDiagonal > reach`. Proof: `target Goal centreDist=22.59` alongside `boxDist 2.000`.
- Confirmed (2026-10-30, PROBED): **`workspace:GetDescendants()` on this place returns thousands of instances, and a single early probe that reported `n=34` was a stale read.** Real numbers: 7210 descendants, 1276 `Part`, 228 `Model`, 40 parts within 60 studs. Rule: a probe that answers a different question than the one asked is a failed call - re-probe before concluding a world is empty. Proof: `desc ok=true n=34` then `desc ok=true n=7210 parts=1276 models=228`.
- Confirmed (2026-10-30): **`Humanoid.PlatformStand` is NOT writable in Matcha.** The writable list is `Name, Parent, Position, Size, CFrame, Velocity, AssemblyLinearVelocity, CanCollide, FieldOfView, AbsolutePosition, AbsoluteSize, Value, WalkToPoint, WalkToPart` - PlatformStand is absent, so the assignment raises `Unknown property`. Inside a `pcall` that error is swallowed and the script appears to do nothing. Proof: the API reference; Wall Walk v1.0 wrapped exactly that write and never changed behaviour.
- Confirmed (2026-10-30): **the only readable `Humanoid` properties are `Health`, `MaxHealth`, `WalkToPoint`, `WalkToPart`.** `WalkSpeed`, `JumpPower`, `Sit` and `PlatformStand` are neither readable nor writable as properties. WalkSpeed lives in the Luau heap: `getgc("WalkSpeed")` / `setgc("WalkSpeed", n)`. Proof: the API reference readable/writable lists.
- Confirmed (2026-10-30): **`Instance` does not exist at all - not merely `Instance.new`.** Nothing can be constructed: no Part, no ScreenGui, no Highlight, no BillboardGui. Every overlay goes through `Drawing`. Proof: the API reference, "DOES NOT EXIST - never call".
- Confirmed (2026-10-30): **assigning `Position`, `CFrame`, `Velocity` or `AssemblyLinearVelocity` performs thousands of internal memory writes per assignment.** A per-frame loop doing it "will destroy the game's framerate". Write on a state change, or throttle; the one legitimate per-frame case is continuous motion the user explicitly asked for. Proof: the API reference PERFORMANCE section.
- Confirmed (2026-10-30): **Instance identity is unstable - two reads of the same Part return wrappers that do not compare equal.** Never use an Instance as a table key and never compare two with `==`; carry the cache entry (a plain Lua table) instead. Proof: the API reference ESP section.
- Confirmed (2026-10-30): **`Players.PlayerAdded` and `PlayerRemoving` return nil** - poll `Players:GetPlayers()` and diff. **`IsA()` ignores its argument and always returns true** - compare `ClassName`. **`UserInputService.InputBegan` gives a table with only `.KeyCode`**, not a Roblox InputObject. Proof: the API reference.
- Confirmed (2026-10-30): **reading an unsupported property does not error - it falls back to `FindFirstChild` and returns nil.** Writing an unsupported property DOES error. A nil read means "unsupported or absent", never "false". Proof: the API reference header.
- Confirmed (2026-10-26): isrbxactive is nil inside matcha_exec (the MCP sandbox), even though it is a real function in a loader-pushed script. The runtime returned a hint saying so. Consequence: a probe can never prove whether input lands. Proof: `focus=err` plus the runtime hint.
- Confirmed (2026-10-26): a matcha_exec chunk is capped at 200 local variables - `Matcha: error: too many local variables (limit is 200, got 205)`. Wide probes silently die; prefer table fields over locals. Proof: piano timing probe that errored, then the trimmed version that ran.
- Confirmed (2026-10-26): `getgc("laneAt")` returned 5 entries whose value is a string, not the module table, so getgc cannot reach a game module's method by key name. Proof: `vtype=string press=nil` for every hit.
- Confirmed (2026-10-26): `RunService.PreRender` is nil in the current build while `RenderStepped` and `Heartbeat` are tables and `:Connect` works. Use RenderStepped or Heartbeat, never PreRender. Proof: `pre=nil render=table hb=table`.
- Confirmed (2026-10-26): `keypress`, `keyrelease`, `isrbxactive` all exist, and `mouse1press`/`mouse1release`/`mouse1click`/`mousemoveabs`/`firetouchinterest`/`fireclickdetector` all exist and return ok=true under pcall. Proof: matcha_exec global sweep.
- Confirmed (2026-10-26): a GuiObject's `AbsolutePosition` can be frozen at one value while the board is idle, but takes a full spread during a live chart. A never-changing AbsolutePosition means "not animating right now", not "unreadable". Proof: idle probes vs the live 8-tile snapshot (y from -194 to 1004).

- User-stated (2026-10-26): `Humanoid.Sit` reads nil for a saddle mount (no Seat or VehicleSeat). Use a `CarriedDino` child or a seat/weld named seat, mount or saddle. Proof: Ride A Dino dump.
- User-stated (2026-10-26): `plot:GetAttribute('Owner')` returns the owning player's UserId as a number on Ride A Dino plots under `Workspace.Pens`. Proof: Ride A Dino dump.
- User-stated (2026-10-26): `UI.GetValue(id)` and `UI.GetValue(name)` both answer; the id form is tried first. Proof: Ride A Dino toggle poller.
